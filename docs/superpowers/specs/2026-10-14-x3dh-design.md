# X3DH identity handshake design

## Intent and status

The user requested an X3DH identity handshake for the existing HeroCrypt Double
Ratchet implementation. Preserve the previously selected HeroCrypt-to-HeroCrypt
scope, the standard classical algorithms, all four library targets and the
requirement that Bouncy Castle is used only for test comparisons.

This document is a proposed design for review. No X3DH implementation or new
security qualification is claimed yet. The intended result is asynchronous,
identity-bound session establishment with signed prekeys and optional one-time
prekeys, followed immediately by the existing Double Ratchet session API.

The application remains responsible for establishing which identity key belongs
to the expected peer. A successful signature is evidence about a key, not an
independent binding of that key to a person or account.

## Selected approach and alternatives

Implement the published X25519/SHA-256 X3DH profile, including XEdDSA signatures
using the X25519 identity key. Add prekey ownership and authenticated initial
message handling alongside the existing ratchet rather than changing its wire
format. This requires a new XEdDSA primitive and explicit lifecycle checks.

Alternatives considered:

- A separate Ed25519 signing key and X25519 identity DH key would reuse current
  primitives, but introduces a custom identity-binding protocol and is not the
  selected standard X3DH profile.
- A native/libsignal dependency supplies more protocol machinery but changes
  the dependency and platform scope. No new runtime crypto package or native
  binary is selected.

Follow the published XEdDSA convention that normalizes the Edwards public-key
sign bit to zero. Current libsignal's signature-sign-bit variant is a different
encoding and is not an interoperability target. Neither this handshake encoding
nor the existing ratchet encoding claims Signal wire interoperability.

## Cryptographic construction

Use 32-byte X25519 identity, ephemeral and prekey private material. Public keys
must be canonical Montgomery u-coordinates. Every DH operation must reject an
all-zero result. Identity and prekey signing uses XEdDSA, not Ed25519 signing of
an X25519 private key interpreted as an Ed25519 seed.

Implement XEdDSA following the published Curve25519 construction: derive the
Edwards public point from the clamped identity scalar, normalize its sign bit
to zero with the corresponding scalar negation modulo the group order, and use
the specified domain-separated SHA-512 signature construction with fresh
64-byte signing randomness. Verify via the corresponding Montgomery-to-Edwards
conversion. Require canonical signature scalars and point encodings and reject
low-order identity keys. Reuse existing limb arithmetic only where its semantics
match; existing RFC 8032 Ed25519 behavior and vectors must remain unchanged.
Do not introduce BigInteger secret arithmetic for this primitive.

Define `Encode(PK)` as byte `0x05` followed by the 32-byte canonical X25519 public
key. Bob signs `Encode(SPK_B)` with `IK_B`. Prekey identifiers route requests;
the standard signature authenticates the signed prekey's public key. No claim
is made that unauthenticated server expiry metadata is trustworthy.

Alice computes, in this exact order:

1. `DH1 = DH(IK_A, SPK_B)`.
2. `DH2 = DH(EK_A, IK_B)`.
3. `DH3 = DH(EK_A, SPK_B)`.
4. If a one-time prekey is present, `DH4 = DH(EK_A, OPK_B)`.

Bob computes the matching values with his private keys and Alice's identity and
ephemeral public keys. Derive a 32-byte `SK` with HKDF-SHA-256: input is 32 bytes
of `0xff` followed by the three/four concatenated DH results, salt is 32 zero
bytes, and info is ASCII `HeroCrypt.X3DH.v1`. Never fall back to three DH values
when a requested one-time key is unavailable or invalid.

Alice verifies the bundle's identity against the required expected identity
before verifying its prekey signature and deriving secrets. Bob compares the
incoming identity with his required expected Alice identity before accepting.
Compare identity bytes in constant time; validate their encodings separately.
Reject an identity mismatch rather than silently learning or replacing a key.

## Binding into Double Ratchet

Initialize Alice's ratchet with `SK` and `SPK_B` as the initial responder public
key. Initialize Bob's ratchet with `SK` and the selected signed-prekey private
key. The ratchet generates Alice's separate initial ratchet key; do not reuse
the X3DH ephemeral key for this purpose.

Compute the ratchet's 32-byte session context as SHA-256 of this unambiguous
transcript, in order:

- ASCII `HeroCrypt.X3DH.DoubleRatchet.v1`.
- Big-endian uint32 application-context length and its bytes (1–4096 bytes).
- `Encode(IK_A)`, `Encode(IK_B)`, `Encode(EK_A)`, `Encode(SPK_B)`.
- Big-endian uint32 signed-prekey identifier.
- One-byte one-time-key presence flag (exactly 0 or 1).
- If present, big-endian uint32 one-time-key identifier and `Encode(OPK_B)`.

For the first ratchet message, its associated-data argument is
`Encode(IK_A) || Encode(IK_B) || uint32be(metadata length) || metadata`.
Application metadata remains caller-supplied expected bytes, not a trusted
field learned from the packet. Bound it to 16 MiB minus the identity/length
prefix so the existing ratchet's associated-data cap is respected. Subsequent
ratchet messages use the existing API, retaining the transcript-bound context.

Initiation produces both a ratchet session and a serialized initial message
containing the first authenticated ratchet ciphertext. Acceptance returns a
session and authenticated first plaintext only after all checks succeed.
Alice has no responder key confirmation until she authenticates a reply.

## Proposed API and ownership

Add `HeroCrypt.Primitives.XEdDsa.XEdDsaBuilder` following existing signature
builder patterns and an internal `XEdDsaCore`. The protocol uses XEdDSA directly;
no new entry in a general algorithm dispatcher is required in this change.

Add types under `HeroCrypt.Protocols.X3dh`:

- `X3dhIdentityKey.Generate(policy = null)` and
  `FromPrivateKey(byte[] privateKey, policy = null)`, a copied `PublicKey`
  property and `IDisposable`. Existing identity private keys can be supplied by
  the application; no new disk storage is introduced.
- `X3dhPreKeyStore.Create(identity, maxOneTimeKeys = 1000,
  maxReplayEntries = 10000, maxRetainedSignedPreKeys = 4, policy = null)`.
  It owns a copy of the identity, generates its initial signed prekey, and
  exposes `GenerateOneTimePreKey()`, `RotateSignedPreKey()`,
  `RetireSignedPreKey(uint id)` and `GetBundle(uint? oneTimePreKeyId = null)`.
  Generation/rotation return the automatically allocated identifier.
- `X3dhPreKeyBundle`: immutable identity public key, signed-prekey identifier,
  public key and signature, with an optional one-time identifier/public key.
- `X3dhHandshake.Initiate(identity, bundle, expectedResponderIdentity,
  applicationContext, firstPlaintext, associatedData = default,
  maxSkippedKeys = 1000, policy = null)` returns an `X3dhInitiation` owning its
  `DoubleRatchetSession` and exposing its immutable `InitialMessage`.
- `store.Accept(initialMessage, expectedInitiatorIdentity, applicationContext,
  associatedData = default, maxSkippedKeys = 1000)` returns an `X3dhAcceptance`
  owning its `DoubleRatchetSession` and the first plaintext.
- `X3dhInitialMessage` and `X3dhPreKeyBundle` provide `FromBytes` and `ToBytes`
  and expose public data as copies.

Identity keys, stores and results implement idempotent disposal. Disposing a
result closes its session; acceptance disposal also clears its owned plaintext.
Document that a caller retaining a plaintext copy must clear that copy itself.
Stores and returned sessions have independent owned buffers; disposing one
must not invalidate another. Never expose `SK`, ephemeral private material or
prekey private material through handshake results or public packet objects.

Validate caps, lengths and policy before cryptographic mutation. Capture the
effective immutable policy and enforce X25519, XEdDSA, HKDF/SHA-256 and the
ratchet's ChaCha20-Poly1305 requirements. A compliance policy that disallows
the primitives rejects the whole profile.

## Prekey lifetime, replay and concurrency

Serialize store operations under a lock, using the repository's target-specific
lock pattern. Allocate monotonically increasing uint32 identifiers in separate
signed/one-time namespaces, starting at 1. Never wrap or reuse an identifier
during the store lifetime. Signed-prekey retention includes the current key;
reject rotation at the cap until the caller retires an older key. Do not retire
the current signed prekey. Unavailable/retired keys reject incoming handshakes.

Publishing `GetBundle` does not consume an OPK. A server may lease that public
bundle to one initiator, but network allocation is application responsibility.
During acceptance, validate the requested keys and replay budget, derive a
candidate session, and authenticate the first message. Only then atomically
register the accepted transcript and remove/clear the selected OPK private key.
All failures dispose the candidate and clear temporary DH/KDF buffers without
changing prekeys or accepted records. Concurrent requests for the same OPK can
produce at most one successful acceptance.

Replay identity is the transcript-context digest; it includes both identity
keys, the ephemeral key, selected prekeys and application context. Record every
accepted handshake, including the no-OPK path. Reject subsequent initial
messages for that accepted transcript even if their first ciphertext differs.
The replay cache is bounded (1–10000 entries), with no silent eviction. Once
full, reject new handshakes until the application establishes a fresh store
with fresh signed/one-time prekeys. Reject OPK generation above its configured
cap (0–10000); signed-prekey cap is 1–32. Failed traffic does not fill the cache.

This version has no prekey-store export/import or restored replay cache. The
application can retain its identity externally, but after restart must generate
and publish fresh signed and one-time prekeys. Do not restore old prekey private
material with an empty replay cache. An OPK-less exchange has the weaker forward
secrecy described by X3DH; it remains an explicitly supported standard path.

## Versioned transport encoding

Use two immutable, bounded HeroCrypt formats, unsigned counters/lengths in
big-endian order. Reject trailing bytes, unknown versions, noncanonical keys,
non-boolean flags, zero identifiers and inconsistent optional fields.

Bundle: four ASCII bytes `HCXB`, version byte 1, identity key (32), signed-key
identifier (4), signed public key (32), XEdDSA signature (64), OPK flag (1), and
if present OPK identifier (4) and public key (32). Exact length is 138 or 174.

Initial message: four ASCII bytes `HCXI`, version byte 1, initiator identity
key (32), initiator ephemeral key (32), signed-key identifier (4), OPK flag (1),
optional OPK identifier (4), ratchet-message length (4), and the exact ratchet
message bytes. Fixed overhead is 78 or 82 bytes. The nested message must meet
the existing 69-byte minimum and 16 MiB plaintext limit; validate lengths with
overflow-safe arithmetic before allocating/copying. All handshake fields are
bound through the session transcript. Transport, directories and accounts are
outside this library change.

## Required validation and review

Test before implementation. XEdDSA needs pinned independent signature fixtures,
Montgomery/Edwards conversion cases, both scalar-normalization branches,
independent signature verification and rejection of tampered/noncanonical,
out-of-range and low-order inputs. BC Ed25519 can verify correctly converted
signatures but is not itself an XEdDSA implementation; use independently
composed fixtures/reference arithmetic for XEdDSA-specific signing behavior.
Preserve all current Ed25519 RFC 8032 tests.

Verify three-DH and four-DH SK derivations independently against BC X25519 and
HKDF, with exact F-prefix, salt, info and DH ordering. Compare initiator and
responder paths and exercise initial-message delivery followed by multi-epoch
ratchet traffic in both directions.

Attack tests must cover identity substitution, invalid prekey signatures,
incorrect context/metadata, selected-key substitution, every initial-header
field, truncated/oversized inputs, low-order contributions, no silent OPK
downgrade, OPK reuse, no-OPK replay, changed ciphertext on an accepted transcript,
cache and key limits, identifier exhaustion, rotation/retirement, concurrent
acceptance, input ownership, disposal and clearing. After rejected traffic,
prove that an authentic initial message can still consume the intended OPK
and complete messaging. Use isolated mutations to check critical assertions.

Run an independent source review of XEdDSA and the complete handshake/store
state transitions before completion. Build all four library targets, run all
existing/new tests on .NET 8/9/10, formatting and package gates, and verify the
actual library package contains neither BC dependencies nor test fixtures.
Add a runnable offline prekey-publication/handshake/messaging example and update
security/profile documents to distinguish implemented X3DH from absent PQXDH,
Signal interoperability, account trust and persistence.

- [Current libsignal sign-bit variant](https://github.com/signalapp/libsignal/blob/4beb029d8a941f81e7d9c6d8af1ed25a677569a8/rust/core/src/curve/curve25519.rs).

No foreign implementation source is copied into production. Any upstream test
fixture added during implementation must include its license and provenance.
The official specification website returned HTTP 403 in this environment;
the pinned reference code was readable. Implementation must validate the exact
published signature/KDF behavior through independently checked fixtures rather
than infer it from a differently encoded libsignal signature.

This feature does not establish an independently audited messaging system,
constant-time execution or complete managed-runtime zeroization. It does not
include PQXDH, network services, TOFU storage, fingerprint UI, persistent stores,
multi-device coordination, prekey leases or automatic identity-key replacement.
