# X3DH Identity Handshake Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Establish identity-bound HeroCrypt Double Ratchet sessions through standard classical X3DH, authenticated prekeys and transactional first-message acceptance.

**Architecture:** Implement normalized-sign-bit XEdDSA over the existing Ed25519 limb arithmetic, then add immutable X3DH packets and independently tested KDF/transcript helpers. An in-memory prekey store owns keys and replay records; it commits acceptance only after the initial ratchet message authenticates. Preserve the existing Double Ratchet API and message encoding.

**Tech Stack:** C#, netstandard2.0/net8.0/net9.0/net10.0, existing HeroCrypt X25519/HKDF/ChaCha20-Poly1305 and .NET SHA-256/SHA-512, xUnit v3, test-only Bouncy Castle.

**Spec:** [Approved X3DH design](../specs/2026-10-14-x3dh-design.md), original approval baseline `ff7ec49`; user approved with “可以”. This plan incorporates the subsequent user-requested independent review corrections.

## Global Constraints

- No new runtime crypto package or native binary. Bouncy Castle remains a private test comparison dependency only.
- Build all four library targets; execute tests on .NET 8/9/10. Keep the pinned SDK `10.0.401` and current lockfiles.
- XEdDSA uses the published normalized-zero Edwards sign bit, fresh 64-byte signing randomness, canonical encodings/scalars and no new BigInteger secret arithmetic. Do not implement libsignal's signature-sign-bit variant.
- `Encode(PK) = 0x05 || PK`; X25519 keys have 32 bytes, signatures have 64 bytes; reject every all-zero DH contribution.
- `SK = HKDF-SHA256(0xff*32 || DH1 || DH2 || DH3 [|| DH4], salt=0x00*32, info=ASCII("HeroCrypt.X3DH.v1"), length=32)` with the spec's exact DH ordering.
- Both roles require the expected peer identity. No automatic identity learning/replacement or fallback after an OPK is selected. OPK availability before selection is not authenticated; callers requiring four-DH must check bundle OPK presence. No Signal wire compatibility, PQXDH, transport or persistent-store API.
- Application context is 1–4096 bytes; first plaintext is at most 16 MiB; metadata is at most `16*1024*1024 - 70` bytes. Ratchet skipped-key budget remains 0–10000.
- OPK cap is 0–10000, replay cap is 1–10000, retained signed-key cap is 1–32 including the current key; defaults are 1000/10000/4. Identifiers start at 1, never wrap or repeat within a store.
- Copy external buffers; dispose owned secret material and unsuccessful candidates. No complete managed-runtime zeroization or constant-time qualification is claimed.
- Initial envelopes require nested ratchet counters `N = PN = 0`. All new return/commit-path byte-buffer cleanup uses nonallocating span clearing; no RNG or explicit GC/finalizer-wait/callback calls follow store commit. Replay storage is preallocated as `32 * maxReplayEntries` bytes, at most 320000 bytes per store.
- Do not push, publish or merge. Use the existing isolated task checkout; keep logs/TRX/temporary mutation copies under `/workspace/setup`.

## Review Focus

- Source identity disposal during store/handshake construction must produce a complete locked snapshot or reject; mutation of caller buffers after copying must not change it (Tasks 4/5).
- Delayed initiation against a rotated signed prekey must remain valid while that key is retained; retirement must reject it without consuming the OPK (Tasks 4/5).
- Empty plaintext/metadata and maximum permitted lengths must agree across framing, KDF and ratchet; adding a length prefix must not overflow the ratchet AD cap (Tasks 2/3/5).
- A hostile request for an OPK, or a valid replay with altered ciphertext, must leave an unused key available and must not create a second session (Task 5).
- Disposal of a store/result must clear its owned buffers without damaging independently owned active sessions or plaintext copies (Tasks 4/5).
